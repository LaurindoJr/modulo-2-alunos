As três partes de uma store

Toda store tem state (os dados), getters (o que se deduz deles) e actions (o que os muda). Vocês já escreveram as três sem saber os nomes. Hoje os nomes entram — e com eles o $patch, o $reset que não existe, e uma medição.

Duas sintaxes, a mesma store

Na setup store não existe this: os ref estão ali mesmo. Na options store o this é a própria store.

Getter que usa outro getter
const concluidas = computed(() => tarefas.value.filter(t => t.concluida).length)
const pendentes  = computed(() => tarefas.value.length - concluidas.value)
MétodoO que faz
$patch({…})Muda vários campos; uma entrada no DevTools

$subscribe(fn)Roda a cada mudança de estado (etapa 23)

Os métodos com $ são da store, não do seu código. Use-os de fora: dentro da setup store os refs estão à mão e não precisam de intermediário.

Mostrar solução (após a tentativa) 
const pendentes = computed(() => tarefas.value.length - concluidas.value)

function contarPor(situacaoPedida) {
  if (situacaoPedida === 'pendentes') return pendentes.value
  if (situacaoPedida === 'concluidas') return concluidas.value
  return tarefas.value.length
}

Quem pode mudar o estado?

Tudo isto é permitido pelo Pinia
store.busca = 'teste'                    // direto
store.$patch({ busca: 'teste' })         // em lote
store.limparFiltros()                    // pela action

const { busca } = storeToRefs(store)
busca.value = 'teste'                    // pelo ref

O Pinia não proíbe mudar o estado de fora. Diferente do Vuex, não há “mutations” obrigatórias. A disciplina é combinada, não imposta.

O critério prático:

SituaçãoComo mudar
Tem regra, validação ou requisiçãoaction
Campo ligado a um v-modeldireto (o ref do storeToRefs) |
Vários campos de uma vez$patch

Por que preferir action quando há regra: ela aparece com nome na linha do tempo. Uma alteração direta aparece como “mudou”, sem dizer quem foi nem por quê. Quando o número estiver errado às onze da noite, o nome é o que você vai querer ter.

Investigação: o $reset que não existe

Console — saída real
> typeof store.$reset
'function'                    ← o método EXISTE

> store.$reset()
Uncaught Error: 🍍: Store "tarefas" is built using the
setup syntax and does not implement $reset().

Repare que ele existe e falha. Não é “método não encontrado”: é o Pinia avisando que, nesta sintaxe, ele não tem como saber o que é o estado inicial.

Dica

Numa options store, o state é uma função: state: () => ({ … }). O Pinia pode chamá-la de novo quando quiser. Na setup store, quem criou os refs foi o nosso código, numa função que já terminou.

As duas saídas
  1. Escrever a sua reiniciar() — o que fazemos.
  2. Usar a options store, se o $reset for importante no seu caso.

Vantagem de escrever à mão: fica explícito o que “estado inicial” quer dizer. Nem sempre é tudo — reiniciar as tarefas não deveria reiniciar o tema.

Guardem o padrão: quando uma biblioteca oferece conveniência, ela precisa saber algo sobre o seu código. A options store conta mais para o Pinia, e recebe mais de volta. Não é melhor nem pior — é uma troca.
