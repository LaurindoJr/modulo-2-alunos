Módulo, pacote, gerenciador e registro

Módulo

Um arquivo que expõe código a outros (module.exports, export). Ex.: relatorio.js.

Pacote

Pasta com um package.json, publicada para reuso. Ex.: picocolors.

Gerenciador (npm CLI)

Programa que lê o manifesto, resolve versões, baixa, instala e executa scripts.

Registro

Serviço que hospeda os pacotes publicados (registry.npmjs.org).

“npm” nomeia duas coisas: o programa no seu computador e o registro na internet. Instalar exige o registro; executar scripts, não.

PerguntaSem internet, quais destes ainda funcionam: npm start, npm install dayjs, npm run?

Fundamento

Dependência é um pacote que o projeto declara precisar. O gerenciador resolve cada requisito para uma versão concreta, baixa do registro e grava em node_modules. Outros gerenciadores (Yarn, pnpm) usam o mesmo manifesto e o mesmo registro, com lockfiles próprios (yarn.lock, pnpm-lock.yaml). Use um gerenciador por projeto.

Resposta da pergunta

npm start e npm run funcionam (usam arquivos locais). npm install dayjs precisa do registro, exceto se o pacote já estiver no cache.

Correção dos materiais

O Laboratório dizia “todos gratuitos” e citava contagens fixas de pacotes. Substitua por critérios de escolha: necessidade, documentação, licença, manutenção e compatibilidade.

Referências

  • npm install

PerguntaPor que o terminal fica ocupado com dev e não com start?

Fundamento

scripts associa nomes a comandos. npm run <nome> executa o comando na pasta do projeto e acrescenta node_modules/.bin ao PATH: por isso nodemon funciona no script sem instalação global. dev é um processo de longa duração (observa arquivos); start termina quando o relatório é impresso. start e test também rodam sem run; os demais precisam de npm run.

Instalação global não é requisito

O Laboratório usava npm install -g nodemon. Global funciona, mas cria diferença entre máquinas e não fica registrada no manifesto. Local + script é reproduzível.

Caso real do npm audit

Os 3 avisos “high” vêm de braces via chokidar@3 via nodemon; o aviso não tem versão corrigida de braces. A sugestão npm audit fix --force instalaria nodemon@1.14.10, versão muito antiga — mudança incompatível. Leia o aviso, avalie o contexto (ferramenta local, padrões definidos por nós) e considere node --watch. Não use --force sem entender o que muda. Saída real de npm audit.

Versão exata, faixa e lockfile

SemVer: MAJOR.MINOR.PATCH — incompatível · nova função compatível · correção.

No manifestoAceita
"1.1.1"só 1.1.1
"~1.1.1"≥ 1.1.1 e < 1.2.0
"^1.1.1"≥ 1.1.1 e < 2.0.0
"^0.27.2"≥ 0.27.2 e < 0.28.0
"^0.0.4"só 0.0.4 (< 0.0.5)

^ não muda o primeiro número diferente de zero. Em 0.x, isso é bem mais restrito.

Manifesto

Requisito: “aceito qualquer 1.x a partir de 1.1.1”.

Lockfile

Resolução: “instalei 1.1.1, deste endereço, com este hash”.

PrevejaSe sair a 1.2.0 amanhã, o que npm install e npm ci fazem nesta pasta?

Fundamento

Uma faixa não é uma versão exata. Sem lockfile, duas instalações em dias diferentes podem resolver versões diferentes. O lockfile registra a árvore resolvida (inclusive transitivas) e é a base de npm ci. Para gravar versão exata no manifesto: npm install --save-exact <pacote>.

Resposta da previsão

npm ci instala 1.1.1 (o lockfile manda). npm install mantém 1.1.1 se o lockfile já satisfaz a faixa; npm update buscaria 1.2.0 e atualizaria o lockfile.

Correções dos materiais

Teórico 5: a explicação do ^ (“patch e minor, não major”) vale para ^3.2.13, mas não para axios ^0.27.2 do mesmo manifesto. Prático 4: não instalar lodash@4.17.20 — versão abrangida por aviso de vulnerabilidade (GHSA-35jh-r3h4-6jhm); para ensinar versão exata, use um pacote realmente necessário, verificado na data.

Limites

O lockfile não elimina diferenças de sistema operacional, versão do Node ou dependências opcionais por plataforma (ex.: fsevents só no macOS).
